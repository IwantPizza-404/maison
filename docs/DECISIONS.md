# Архитектурные решения

Почему проект устроен именно так. Перед тем как менять что-то из этого списка — прочитать причину.

## Стек

| Решение | Почему | Что рассматривали |
|---|---|---|
| **Django 5.2 LTS** на бэкенде | Готовая админка, зрелая ORM, LTS до 2028, Python-разработчиков легко найти в Узбекистане | Laravel + Lunar + Filament (отказались: разработчик против PHP); Medusa v2 (слабее админка, React); FastAPI (нет админки) |
| **Nuxt 4** (Vue) на витрине | Требование разработчика — Vue; SSR для SEO. rivolishop тоже на Nuxt | — |
| **Nuxt UI 4** как UI-kit | Предложение разработчика: не писать базовые компоненты самим; Tailwind 4 + Reka UI, доступность из коробки | shadcn-vue, PrimeVue |
| **Django Admin + Unfold** | Админка без написания фронтенда; вкладки переводов, фильтры, бейджи | Своя админка на Vue (месяцы работы) |
| **Django Ninja** | Типизированное API + OpenAPI → TS-типы фронтенда (`make api-types`) | DRF |
| **Модульный монолит** | Чёткие границы модулей (`apps/*`) без сложности микросервисов | Микросервисы — преждевременно |

## Данные и бизнес-логика

- **Цены только в USD.** Другие валюты — пересчёт для отображения. Заказ фиксирует курс. Так нет рассинхрона цен в разных валютах.
- **Валюты отображения — записи в админке**, а не настройка: заказчик сам добавляет валюту. Курс берётся из ЦБ, если ЦБ её публикует, иначе — ручной.
- **Характеристики часов — отдельная модель `WatchSpecs`** (OneToOne с `Product`), чтобы у ремешков/аксессуаров не было пустых полей часов.
- **Справочник `SpecOption`** вместо `choices`: заказчик сам добавляет и переводит значения фильтров.
- **Позиция заказа — снимок товара** (бренд, название, цена): товар потом могут изменить или удалить.
- **Резерв остатков с `select_for_update`**: последний экземпляр нельзя продать дважды.
- **Заказы не удаляются, только отменяются** — остатки всегда сходятся.
- **Корзина в cookie на клиенте**, расчёт — на сервере (`/cart/quote`): работает без регистрации, цены всегда актуальны.
- **Статус заказа по секретному токену** в URL — без регистрации покупателя.
- **Способы доставки — справочник в админке**, а не код: заказчик меняет условия сам.

## Контент

- **Главная — секции в админке, а не вёрстка в коде**: заказчик сам меняет баннеры и подборки под акции (как у rivolishop с их CMS).
- **Контакты и соцсети — в настройках сайта (админка)**, а не в переменных окружения: заказчик меняет их без разработчика.
- **Мега-меню собирается автоматически** из брендов с товарами и фиксированных подборок — не требует настройки.

## Медиа

- **WebP-варианты 400/800/1600 px строит бэкенд** (Celery) при загрузке, витрина отдаёт `srcset`. Отказались от `@nuxt/image` (IPX): ресайз на лету нагружает сервер витрины.
- **Общий механизм `ResponsiveImagesMixin`** (`core/responsive.py`) для баннеров и плиток: варианты и размеры хранятся в JSON-поле — размеры не читаются из файла на каждый запрос (на S3 это сетевой вызов).
- **HEIC (iPhone)** поддерживается через `pillow-heif` — заказчик будет снимать на телефон.
- Локально медиа на диске, в продакшене — S3-совместимое хранилище (Cloudflare R2). MinIO не используем: перестал публиковать открытые образы.

## Переводы

- Контент — `django-modeltranslation` (поля `*_en/_ru/_uz`, фолбэк на английский).
- Интерфейс админки — gettext (`locale/`). **`makemessages` переопределён с `--no-fuzzy-matching`**: иначе gettext подставляет похожие, но неверные переводы («Orders» → «Под заказ»).
- Одинаковые английские слова с разным смыслом разводятся контекстом: `pgettext_lazy("order status", "New")`.
- Витрина — `@nuxtjs/i18n`, файлы `frontend/i18n/locales/*.json`.

## Личный кабинет

- **Покупатели — отдельная модель `Customer`**, не `User` админки: сотрудники и покупатели не смешиваются.
- **Вход без пароля**: Telegram-бот (основной — аудитория в Telegram, бесплатно, телефон подтверждается), SMS и WhatsApp (Cloud API Meta, шаблон авторизации; платно, включается ключами).
- **Код вводится на сайте, а не «подтвердить вход» в боте**: иначе злоумышленник мог бы прислать жертве
  ссылку со своим токеном и войти в её аккаунт.
- **Сессия — HttpOnly-cookie**, в базе только хэши ключей и кодов. CSRF закрыт SameSite=Lax + JSON-API.
- **Лимиты**: 5 попыток кода (счётчик вне транзакции — иначе откатывался бы), 3 SMS/час на номер.
- **Гостевые заказы привязываются по подтверждённому телефону** (`Order.phone_normalized`).
- **Один бот** для входа, уведомлений покупателям и менеджеру; вебхук в продакшене, polling локально.

## Оплата и уведомления

- **Онлайн-оплаты нет** — у заказчика нет ЯТТ. Оплату согласует менеджер. Платёжные провайдеры добавятся отдельным модулем.
- **Уведомления менеджеру — Telegram-бот** (аудитория и заказчик живут в Telegram). Без токена бота заказ всё равно создаётся.

## Продакшен

- **Один VPS + Docker Compose**: для магазина такого масштаба проще и дешевле Kubernetes.
- **Caddy** вместо nginx: HTTPS-сертификаты выпускаются и продлеваются автоматически.
- **Сайт и API на одном домене** (`/api` проксируется на Django): нет CORS, cookie работают просто.
- **Редирект на HTTPS — только в Caddy**, не в Django: витрина при SSR ходит к бэкенду по внутренней сети по http.
- **`MEDIA_URL` абсолютный** (`https://домен/media/`): иначе при SSR ссылки на фото строились бы от `backend:8000`.
- **`NINJA_NUM_PROXIES = 1`**: лимит заказов считает реальный IP покупателя, а не IP Caddy.
- **Индексация закрыта по умолчанию** (`NUXT_INDEXABLE=false`): тестовый сервер не попадёт в Google.

## Окружение

- PostgreSQL в Docker на порту **5433** — 5432 занят локальным Postgres разработчика.
- **Node 24 LTS** (`.nvmrc`): часть пакетов не поддерживает Node 23.
- TypeScript 5.9 (не 7): совместимость с `vue-tsc`.
- Локально Celery выполняет задачи синхронно (`CELERY_EAGER=true` по умолчанию в dev).
